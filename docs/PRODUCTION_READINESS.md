# 线上就绪审计

> 2026-09-09 更新：本文保留历史审计结论。需求及模型访问权限、生产初始化拆分和迁移部署步骤已完成代码修复；当前流程见 [生产初始化](./PRODUCTION_INITIALIZATION.md) 和 [数据库迁移与部署](./DATABASE_MIGRATIONS.md)。目标生产环境仍需验收。

> 审计日期：2026-08-28 · 范围：交换微信联系方式之前的完整业务链路

## 结论

**当前不能按仓库默认生产方式直接上线。**

应用层主链路已经具备：手机号登录、微信资料、需求发布、管理员审核、联系方式申请、所有者同意、私有通知披露微信号。生产部署层仍有阻塞项，且缺少该链路的数据库集成测试，因此当前结论是“业务实现基本闭合，生产发布未就绪”。

## 上线阻塞项

### P0-1：阿里云 OSS 真实环境尚未验证

代码已实现 `AliyunOssStorageAdapter`，并按 `STORAGE_PROVIDER` 完成装配。上线前仍需：

- 创建私有 OSS Bucket；
- 配置最小权限 RAM 身份；
- 注入生产 Secret；
- 验证上传、签名下载和服务重启后的文件可用性。

### P0-2：生产容器不执行数据库迁移

API 镜像只启动 Node 进程，compose 没有 migration job。未人工执行 `prisma migrate deploy` 时，`wechatId`、`ContactRequest`、`Notification.demandId` 均不存在，主链路会失败。部署流水线必须在新 API 启动前执行迁移。

### P0-3：缺少联系方式链路集成测试

现有测试未覆盖：申请事务、所有权隔离、重复申请、并发同意、微信号通知仅申请人可见、迁移后的真实 PostgreSQL 行为。上线前至少需要一个 PostgreSQL 集成测试覆盖完整双用户流程。

## 非阻塞但应尽快修复

### P1-1：已打开详情页的申请列表不会实时刷新

SSE 只失效 `notifications/demands/my-demands/demand`，没有失效 `contact-requests`。需求方停留在详情页时，新申请不会自动出现，需刷新页面。

### P1-2：联系方式只存在最近 50 条通知中

通知接口固定取 50 条，没有分页或独立的已批准联系方式页面。通知较多后，用户无法重新查找旧微信号。

### P1-3：申请资格不校验打印设备

任何登录用户都可以申请联系方式，不要求登记设备，也不校验设备尺寸、材料或状态。这符合当前代码，但弱于“接单方”业务语义。

### P1-4：需求缺少关闭入口

需求方找到合作方后不能关闭需求，其他用户仍可继续提交申请。

### P1-5：审核结果没有通知

管理员通过或驳回只更新状态，不创建需求方通知。需求方必须在工作台查看结果。

### P1-6：公开详情不校验需求状态

知道需求 ID 的访问者可以请求待审核或驳回需求详情及模型 URL。虽然收货信息已剔除，但未审核模型仍可能被访问。

## 已验证能力

- Prisma schema 有联系方式字段、申请模型、关系、索引和唯一约束。
- 创建需求前后端均检查微信号。
- 公开需求响应不返回微信号、收件人、电话和详细地址。
- 创建申请时禁止本人申请并防重复。
- 申请列表只允许需求所有者读取。
- 同意申请只允许记录所有者操作，并使用条件更新防并发。
- 同意事务中同时写批准状态和含微信号的申请人通知。
- 通知查询、单条已读均按当前用户过滤。
- TypeScript 检查、现有 API/Web 测试和生产构建通过。
- 生产启动不再强制配置支付供应商。
- 用户名密码注册、登录、密码字段和密码依赖已移除，认证统一为手机号验证码。
