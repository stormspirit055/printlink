# 印蛙上线准备审计

> 2026-09-09 更新：本文保留历史审计结论。模型访问权限、生产初始化拆分和迁移部署步骤已完成代码修复；当前操作流程见 [生产初始化](./PRODUCTION_INITIALIZATION.md) 和 [数据库迁移与部署](./DATABASE_MIGRATIONS.md)。生产环境验收仍待完成。

> 审计日期：2026-08-30  
> 审计范围：当前 Vue Web、Express API、PostgreSQL、Redis、文件存储、短信、Docker 部署，以及从用户准入到微信联系方式披露的完整业务流程  
> 目标版本：联系方式撮合版，不包含平台内报价、订单、支付、生产、物流、售后和争议处理

> 本文按完整生产运营标准审计。邀请制、小规模最基础版本请使用 [`MVP_LAUNCH_GAP_CHECKLIST.md`](./MVP_LAUNCH_GAP_CHECKLIST.md)，不要将本文所有完善项视为 MVP 上线阻塞项。

## 1. 结论

**当前不能正式上线。**

核心业务代码已经形成以下闭环：

```text
管理员创建邀请码
  -> 用户获取短信验证码并登录/注册
  -> 用户填写微信号
  -> 需求方创建地址并上传 3MF
  -> 管理员审核需求
  -> 接单方浏览需求并申请联系方式
  -> 需求方同意申请
  -> 系统通过申请人的私有通知披露微信号
  -> 双方转至微信沟通
```

但是，生产部署、模型访问控制、生产初始化、真实环境测试和运维保障尚未达到上线要求。仓库当前有 **7 项 P0 阻塞项**。解决全部 P0 后，可以进行小流量试运营验收；P1 项应在公开推广前完成。

## 2. 当前产品边界

### 2.1 可以作为本期上线范围的能力

| 角色   | 已实现流程                                     | 当前状态                     |
| ------ | ---------------------------------------------- | ---------------------------- |
| 管理员 | 创建和停用邀请码                               | 已实现                       |
| 用户   | 手机号验证码登录，新手机号使用邀请码注册       | 已实现，依赖真实短信服务     |
| 用户   | 编辑昵称、微信号和简介                         | 已实现                       |
| 需求方 | 创建和管理收货地址                             | 已实现                       |
| 需求方 | 上传 3MF、浏览器解析模型、生成参考价并提交审核 | 已实现，服务端可信校验不足   |
| 管理员 | 预览模型，通过或驳回需求                       | 已实现                       |
| 接单方 | 浏览已通过需求，申请需求方微信号               | 已实现                       |
| 需求方 | 查看申请并同意披露微信号                       | 已实现                       |

### 2.2 不属于本期上线范围的功能

当前版本不提供站内报价、订单、支付、履约和评价。前端不展示订单入口或统计，API 不挂载订单、支付、履约或评价路由，配置也不接受支付供应商。相关路径统一返回 `404 RESOURCE_NOT_FOUND`。

为后续扩展保留 Prisma 数据模型和纯订单领域状态规则，但不保留可运行的应用服务、支付网关或数据仓储实现。未来实现时，按 `domain -> application -> infrastructure -> routes` 分层接入，并通过显式路由挂载进入产品运行面。

## 3. 业务流程审计

### 3.1 用户准入与登录

流程：管理员创建邀请码 -> 用户请求验证码 -> 短信服务发送验证码 -> 新用户提交邀请码 -> 系统创建用户和 30 天会话。

已具备：

- 验证码存储于 Redis，有 5 分钟有效期。
- 登录和验证码接口有 Redis 支持的 IP 限流。
- 同一手机号有发送冷却时间。
- 邀请码使用次数通过条件更新控制，能处理并发超额使用。
- 会话令牌只保存哈希；生产 Cookie 使用 `HttpOnly`、`Secure` 和 `SameSite=Lax`。

上线缺口：

- 必须申请并联调阿里云或腾讯云短信签名与模板，验证成功、失败、限流、余额不足和供应商超时场景。
- 当前 seed 会创建固定手机号管理员、两个测试用户和固定邀请码 `WELCOME1`。生产环境不能直接执行现有 seed。
- 缺少管理员首次初始化、身份交接、权限回收和紧急停用流程。
- 缺少异常登录监控、验证码发送成本告警和手机号维度的验证码尝试次数限制。当前登录接口虽有 IP 限流，但分布式 IP 可绕过单 IP 防护。
- 缺少隐私政策、用户协议、个人信息处理规则和账号注销/数据删除流程。

### 3.2 个人资料与地址

流程：用户填写微信号 -> 创建收货地址 -> 发布需求时将地址复制为需求快照。

已具备：

- 发布前，前端和后端都检查微信号。
- 地址接口按当前用户隔离。
- 省、市、区组合在后端校验。
- 公开需求响应会移除收件人、电话和详细地址。

上线缺口：

- 手机号、微信号和详细地址属于个人信息，需要明确保存期限、删除策略、访问审计和客服查询权限。
- 用户删除地址不会删除需求中的历史地址快照，产品和隐私政策必须说明该行为。
- 没有账号注销接口，也没有注销后的地址、模型、通知和联系方式申请处理规则。

### 3.3 3MF 上传、解析和发布

流程：浏览器解析 3MF -> 浏览器计算参数和参考价 -> API 仅检查扩展名和文件大小 -> 保存文件 -> 创建 `PENDING_REVIEW` 需求。

已具备：

- 只允许单文件上传，默认最大 50 MB。
- Multer 将上传写入临时目录，业务处理结束后删除临时文件。
- 需求保存收货地址快照，公开列表不返回地址和 `modelKey`。

上线缺口：

- 服务端只校验 `.3mf` 扩展名，没有校验 ZIP/3MF 文件结构、MIME、解压大小、压缩炸弹、恶意内容或模型可解析性。
- 尺寸、体积、耗材、工时、材料、颜色和预算由客户端提交，服务端直接信任。恶意客户端可伪造制造参数和参考价。
- 文件先保存、后创建数据库记录。数据库写入失败时，已保存文件不会删除，会产生孤儿文件。
- 删除需求和清理废弃模型的生命周期尚未实现。
- 缺少上传容量、失败率、存储用量和异常文件告警。

### 3.4 管理员审核与公开展示

流程：管理员查看待审核需求和模型 -> 通过后状态变为 `OPEN` -> 大厅展示；驳回后状态变为 `REJECTED`。

已具备：

- 审核接口要求管理员权限。
- 只有 `PENDING_REVIEW` 状态可审核，条件更新能避免重复审核。
- 大厅列表只返回 `OPEN` 和历史 `QUOTED` 需求。

上线缺口：

- `GET /api/demands/:id` 不校验状态和访问者身份。任何知道需求 ID 的人都能读取待审核或已驳回需求详情。
- `/uploads/:key` 是公开静态文件。模型 URL 不是真正的签名 URL，审核前模型可以被访问和传播。这会绕过内容审核，也会增加模型知识产权泄露风险。
- 驳回原因允许为空；需求方不会收到审核结果通知，只能主动查看工作台。
- 没有审核记录表，无法追溯审核人、审核时间、原始结果和后续改动。
- 没有内容违规分类、举报、下架、封禁和证据保留流程。

### 3.5 联系方式申请和授权披露

流程：接单方申请 -> 系统在事务中创建申请和需求方通知 -> 需求方同意 -> 系统在事务中更新申请并向申请人发送含微信号的通知。

已具备：

- 仅登录用户可以申请。
- 需求所有者不能申请自己的联系方式。
- 数据库唯一约束阻止同一用户重复申请同一需求。
- 申请列表只允许需求所有者读取。
- 同意操作校验 `ownerId`，并通过条件更新处理并发同意。
- 微信号只写入被同意申请人的通知，没有进入公开需求响应。

上线缺口：

- 缺少真实 PostgreSQL 集成测试，尚未验证事务、唯一约束、并发同意、所有权隔离和微信号可见范围。
- 任何登录用户都能申请，不要求登记打印机，也不校验打印尺寸、材料、地点或账号状态。
- 申请不能拒绝、撤回或过期。需求也不能关闭，达成合作后仍可继续收到申请。
- 需求方后续修改微信号不会更新已发送通知。产品需要明确授权披露的是同意时的微信号快照。
- 缺少联系方式滥用举报、用户拉黑、申请频率限制和风控策略。

### 3.6 通知和实时更新

已具备：

- 通知查询、单条已读和全部已读均按当前用户过滤。
- Redis Pub/Sub 支持多实例间的 SSE 事件分发。
- SSE 有心跳，并设置 `X-Accel-Buffering: no`。

上线缺口：

- 通知接口固定返回最近 50 条，没有分页、归档或独立的已授权联系方式页面。旧微信号可能无法从界面找回。
- SSE 事件不会失效 `contact-requests` 查询。需求方停留在详情页时，新申请不会自动显示。
- Nginx 没有针对 SSE 单独配置读取超时和代理缓冲策略，需要在目标网关、CDN 和负载均衡器上实际验证长连接。
- 缺少通知投递失败指标、SSE 连接数、重连率和 Redis Pub/Sub 异常告警。

### 3.7 线下交易和平台责任边界

微信号披露后，价格协商、付款、生产、物流、售后和争议全部在线下完成。系统没有成交确认、需求关闭、评价、退款、证据留存和争议处理入口。

正式运营前必须明确：

- 平台是信息撮合方还是交易参与方。
- 用户欺诈、侵权模型、人身财产损失和交易纠纷的处理方式。
- 禁止发布的模型类型和审核标准。
- 客服入口、投诉时限、封禁规则和执法协查流程。
- 平台展示的「参考价」不构成报价或履约承诺。

以上内容需要产品、运营和法律共同确认。仅完成技术部署不能覆盖这些风险。

## 4. 上线阻塞项

### P0-1：阿里云 OSS 真实环境尚未配置和验证

代码已经按 `STORAGE_PROVIDER` 装配 `LocalStorageAdapter` 或 `AliyunOssStorageAdapter`，并校验 OSS 必填配置。生产 Bucket、RAM 权限和真实上传下载仍需在阿里云环境完成。

处理要求：

1. 创建私有 OSS Bucket。
2. 配置仅允许 `models/*` 读写的 RAM 身份。
3. 通过 Secret 注入 OSS 凭证。
4. 完成真实上传、签名下载和 API 重启验证。

### P0-2：模型访问控制绕过审核

公开详情接口会返回任意状态需求的模型 URL，`/uploads` 也无需认证。待审核、已驳回和已关闭模型不能与公开模型使用同一访问策略。

处理要求：

1. 公开详情只允许读取公开状态需求。
2. 需求所有者和管理员通过鉴权接口读取非公开需求。
3. 文件保持私有，通过短期签名 URL 或鉴权下载接口访问。
4. 增加匿名、其他用户、所有者和管理员的访问矩阵测试。

### P0-3：生产部署不执行数据库迁移

API 镜像直接启动 Node 进程，Compose 没有 migration job。`/health/ready` 只执行 `SELECT 1` 和 Redis `PING`，不能发现数据库 schema 版本过旧。

处理要求：

1. 在发布流水线或一次性 migration job 中运行 `prisma migrate deploy`。
2. 迁移成功后再启动新 API。
3. 迁移失败时停止切流。
4. 为破坏性迁移制定备份、回滚或前向修复方案。

### P0-4：缺少核心链路的真实数据库集成测试

现有测试主要是单元测试和浅层路由测试，没有使用真实 PostgreSQL 覆盖联系方式业务闭环。

至少需要覆盖：

1. 三个身份：需求方、申请人、无关用户。
2. 发布、审核、申请、重复申请、同意和重复同意。
3. 两个并发同意请求只产生一条授权通知。
4. 只有申请人的私有通知包含微信号。
5. 非所有者不能读取申请列表或执行同意。
6. 迁移后的 PostgreSQL 和 Redis 环境重启后数据仍存在。

### P0-5：生产初始化脚本包含演示身份和固定邀请码

现有 seed 创建固定管理员手机号 `13800000000`、两个测试用户、测试微信号、测试打印机和邀请码 `WELCOME1`。生产环境执行该 seed 会引入可预测的账号与邀请码。

处理要求：

1. 将基础计价数据 seed 与演示数据 seed 分离。
2. 生产管理员通过一次性、可审计的初始化流程创建。
3. 生产邀请码必须随机生成，不得包含固定公共邀请码。
4. 在部署验收中检查生产库不存在演示账号、测试设备和固定邀请码。

### P0-6：仓库发布检查未通过

2026-08-30 复验时，TypeScript、ESLint、全部测试和生产构建通过。`npm run check` 仍在 Prettier 检查阶段失败，剩余 5 个未触及文件存在格式差异。发布门禁当前不是全绿状态。

处理要求：单独确认并格式化剩余文件，再运行完整 `npm run check`，并将该命令设为 CI 必须通过的发布门禁。

### P0-7：缺少可执行的生产拓扑和安全配置

当前 Compose 更接近本地运行配置：PostgreSQL 使用固定弱密码，PostgreSQL 和 Redis 端口直接映射到宿主机，Web 只监听 HTTP 8080，没有 TLS 终止、Secret 管理、容器健康检查、资源限制和独立备份任务。

处理要求：

1. 明确生产运行平台、域名、TLS 终止点、反向代理和网络边界。
2. 使用部署平台 Secret 注入数据库、Redis、短信和会话密钥。
3. 不向公网暴露 PostgreSQL 和 Redis。
4. 为 Web 和 API 配置健康检查、滚动发布、资源限制和日志采集。
5. 配置 PostgreSQL、Redis 和模型文件的备份、恢复演练和保留策略。
6. 配置监控、告警、错误追踪和审计日志。

## 6. P2 改进项

- 删除或生产禁用 `/dev` 路由，避免内部演示页对正式用户可见。
- 清理旧 `public/server/data` 原型，明确唯一生产代码路径，降低误部署风险。
- 清理测试运行结束时 Redis store 的异步报错噪声，避免真实失败被日志淹没。
- 为通知、申请、需求和地址接口增加分页。
- 为 API 增加请求 ID 的端到端透传，并建立结构化日志字段规范。
- 校验 `WEB_ORIGIN`、代理层 `Host`、`X-Forwarded-*` 和 Cookie 行为是否符合实际多域名拓扑。
- 评估 Web 构建产物体积。当前 Naive UI 和 Three.js chunk 较大，应在真实移动网络验证首屏和模型预览加载性能。

## 7. 基础设施与运维缺口

### 7.1 数据与恢复

上线前必须定义并验证：

- PostgreSQL 自动备份、保留周期和恢复步骤。
- Redis 的用途边界。会话在 PostgreSQL，验证码、限流和实时消息依赖 Redis。
- 模型文件备份和数据库 `modelKey` 的一致性检查。
- 数据库迁移前快照和迁移失败处理。
- 恢复后的 RPO、RTO 目标。具体数值由业务方确认。

### 7.2 可观测性

至少需要监控：

- API 请求量、P95/P99 延迟、4xx/5xx 比例和进程重启次数。
- PostgreSQL 连接数、慢查询、磁盘和备份状态。
- Redis 连接、内存、命中、持久化和 Pub/Sub 状态。
- 短信发送成功率、供应商错误码、发送量和费用。
- 上传成功率、文件大小、存储容量和下载失败率。
- 注册、发布、审核、申请、同意各步骤的漏斗与异常率。
- SSE 在线连接数、断开和重连频率。

### 7.3 安全

上线前至少完成：

- Secret 轮换和最小权限访问。
- 数据库、Redis 和对象存储的网络隔离。
- 依赖漏洞扫描和镜像扫描。
- 上传文件安全策略和私有访问策略。
- 管理员操作审计。
