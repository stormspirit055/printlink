# 印蛙最基础版本上线查漏补缺

> 检查日期：2026-08-30  
> 版本范围：邀请制、小规模、人工运营的微信联系方式撮合版  
> 核心目标：用户能够登录、发布需求、完成审核、申请联系方式，并在授权后取得微信号

## 1. 结论

当前核心业务功能已经基本完成，但仓库还不能直接按生产配置上线。

最基础版本只需要解决 **6 项上线必需问题**：

1. 确定并修正生产文件存储方案。
2. 在部署时执行数据库迁移。
3. 配置并验证真实短信服务。
4. 分离生产初始化数据和演示数据。
5. 阻止未审核模型被公开访问。
6. 准备能维持登录和数据持久化的生产运行环境。

其余功能可以在上线后根据实际使用情况逐步完善。

## 2. 最基础业务闭环

首版只验收以下流程：

```text
管理员创建邀请码
  -> 新用户通过手机号和邀请码登录
  -> 用户填写微信号
  -> 需求方创建地址并上传 3MF
  -> 管理员通过或驳回需求
  -> 已通过需求进入需求大厅
  -> 其他用户申请微信联系方式
  -> 需求方同意申请
  -> 申请人从私有通知中取得微信号
```

站内报价、订单、支付、生产、物流、售后和评价不属于首版范围。相关前端入口和运行时 API 已移除，数据库模型仅为后续扩展保留。

## 3. 上线前必须解决

### 3.1 配置生产 OSS

现状：阿里云 OSS 适配器、provider 装配、生产配置校验和签名 URL 已实现。上线前还需要创建私有 Bucket、配置 RAM 权限并完成真实环境验证。

最小解决方案：

- 按 `ALIYUN_OSS_SETUP.md` 创建私有 Bucket 和 RAM 身份。
- 设置 `STORAGE_PROVIDER=oss` 及 OSS 环境变量。
- 上传模型并验证签名 URL。
- 验证 API 容器重启后，已上传模型仍可访问。

代码实现已完成，真实阿里云资源配置仍待执行。

验收结果：生产配置能够启动；上传模型后重启 API，模型仍然存在。

### 3.2 在部署过程中执行数据库迁移

2026-09-09 代码更新：已补齐起始建表迁移和当前结构修正；Compose 新增一次性 `migrate` 服务，API 等待迁移成功。`npm run deploy` 每次执行新迁移任务，失败时停止更新应用。已有库接管及失败处理见 [数据库迁移与部署](./DATABASE_MIGRATIONS.md)。目标生产库执行仍待验收。

最小解决方案：在启动新 API 前执行一次：

```bash
npx prisma migrate deploy --schema apps/api/prisma/schema.prisma
```

迁移失败时，不启动新 API。首版可以使用人工部署步骤或一次性容器，不要求先建设完整 CI/CD 平台。

验收结果：空数据库迁移成功，API 启动后 `/health/ready` 返回 `200`。

### 3.3 配置真实短信服务

现状：开发环境的 `console` provider 会在响应中返回验证码，生产环境已经禁止该 provider。没有真实短信配置时，用户无法登录。

最小解决方案：

- 在阿里云或腾讯云中选择一个短信供应商。
- 准备已审核通过的签名和验证码模板。
- 通过 Secret 注入对应凭证。
- 使用真实手机号完成一次验证码发送和登录。

首版只需验证正常发送、错误验证码和发送冷却。短信费用监控、复杂反滥用策略可以后补。

验收结果：新用户和老用户都能通过真实短信完成登录。

### 3.4 分离生产初始化数据

2026-09-09 代码更新：`db:seed` 已改为仅初始化基础计价数据；演示数据移至 `db:seed:demo`，生产环境禁止执行。`db:init-admin` 用于创建首个正式管理员，支持幂等执行和并发保护。操作步骤见 [生产初始化说明](./PRODUCTION_INITIALIZATION.md)。目标库执行及既有演示数据检查仍待上线验收。

最小解决方案：

- 保留材料、颜色和计价规则的基础数据初始化。
- 不在生产库创建测试用户、测试打印机和 `WELCOME1`。
- 通过一次性脚本或数据库操作创建首个管理员，手机号由上线负责人提供。
- 管理员登录后，通过后台生成正式邀请码。

首版不要求建设完整的管理员生命周期管理功能。

验收结果：生产库存在基础计价配置和一个可登录管理员，不存在演示用户与固定邀请码。

### 3.5 限制未审核模型访问

2026-09-09 代码更新：需求详情要求登录；`OPEN`、历史 `QUOTED` 状态允许登录用户访问，其他状态仅发布者和管理员可见。`/uploads/:key` 已改为关联需求鉴权下载，关闭公开静态目录。OSS 链接在详情鉴权通过后签发。目标环境仍需验证私有 Bucket 配置及账号权限。

最小解决方案：

- `OPEN` 需求允许登录用户查看详情和模型。
- `PENDING_REVIEW`、`REJECTED` 需求只允许需求所有者和管理员查看。
- 模型下载通过鉴权接口完成，不再直接公开整个上传目录。

首版不必实现 OSS 签名 URL、病毒扫描或复杂内容风控，但不能让审核机制被公开文件路径绕过。

验收结果：普通用户不能查看其他用户的待审核或已驳回需求及模型；需求所有者和管理员可以查看。

### 3.6 准备最小生产运行环境

现状：当前 Compose 主要面向本地环境。生产登录 Cookie 使用 `Secure`，如果没有 HTTPS，登录会话无法正常保存。PostgreSQL、Redis 和上传目录也必须持久化。

最小解决方案：

- 准备一个正式域名并启用 HTTPS。
- 设置正确的 `WEB_ORIGIN`。
- 生成不少于 32 字符的随机 `SESSION_SECRET`。
- 不使用仓库中的默认数据库密码。
- PostgreSQL、Redis 和上传目录使用持久卷。
- PostgreSQL 和 Redis 不直接暴露到公网。
- Web 能够反向代理 `/api`、`/health` 和模型访问接口。

首版可以采用单机 Docker Compose，不要求负载均衡、滚动发布、集中日志或自动扩容。

验收结果：通过正式域名登录后刷新页面，会话仍然有效；重启全部容器后，账号、需求、申请、通知和模型仍然存在。

## 4. 上线前人工验收

准备三个账号：一个管理员、一个需求方、一个申请人。按顺序执行：

1. 管理员登录并创建邀请码。
2. 需求方使用真实短信和邀请码完成首次登录。
3. 需求方填写微信号并创建收货地址。
4. 需求方上传一个有效 3MF 并提交需求。
5. 确认提交前，申请人不能在大厅看到该需求。
6. 管理员查看模型并通过需求。
7. 确认申请人能在大厅和详情页查看该需求。
8. 申请人提交联系方式申请。
9. 需求方收到通知，并在需求详情中看到申请。
10. 需求方同意申请。
11. 申请人收到含正确微信号的私有通知。
12. 使用另一个无关账号确认不能读取该微信号。
13. 重启全部容器，再次确认需求、申请、通知和模型可用。

任何一步失败，都应停止上线并修复对应问题。

## 5. 可以延期的事项

以下内容属于业务完善或工程完善，不阻塞邀请制最基础版本上线：

- 需求关闭、申请拒绝、撤回和过期。
- 通知分页、归档和独立联系人列表。
- 审核结果主动通知。
- 打印设备与申请资格匹配。
- 服务端重新计算 3MF 参数和参考价。
- 上传文件病毒扫描、压缩炸弹检测和孤儿文件清理。
- 账号注销、用户拉黑、举报和复杂风控。
- 完整审核日志和管理员权限生命周期。
- 自动化 PostgreSQL 集成测试和浏览器 E2E。
- 集中日志、指标监控、错误追踪、自动告警和审计平台。
- 自动备份、恢复演练、滚动发布、自动扩容和多实例部署。
- 依赖漏洞扫描、镜像扫描和完整安全测试。
- 弱网性能优化和前端构建体积优化。
- 站内报价、订单、支付、履约、售后和评价。

这些事项不是“不需要做”，而是不要求在首批受控用户进入前全部完成。出现真实业务需求或准备扩大开放范围时，应重新评估优先级。
