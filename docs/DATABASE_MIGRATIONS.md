# 数据库迁移与部署

## 执行入口

| 命令 | 用途 |
| --- | --- |
| `npm run db:migrate` | 开发环境生成和测试新迁移；不要用于生产 |
| `npm run db:deploy` | 对目标库执行仓库中尚未应用的迁移 |
| `npm run db:status` | 查看迁移记录与待执行迁移 |
| `npm run db:adopt` | 将结构已完全匹配当前模型的已有库接入迁移管理 |
| `npm run deploy` | 构建镜像、启动数据库依赖、执行本次迁移，成功后更新 API 和 Web |

本地数据库命令会加载项目根目录的 `.env`；环境中已注入的同名变量优先，因此部署平台仍可通过 Secret 指定目标库。Compose 会读取 `.env`，并按 `docker-compose.yml` 配置容器内数据库地址。执行前请先核对目标地址。

## 新数据库首次部署

先准备生产配置、数据库持久卷和真实短信、OSS 等依赖。当前 Compose 中的默认密码和宿主机数据库端口仍需按生产网络要求调整。

在项目根目录执行：

```bash
npm run deploy
```

执行顺序：

1. 构建 API、Web 和迁移镜像。构建失败时退出。
2. 启动 PostgreSQL 和 Redis，并等待健康检查通过。
3. 创建一次性迁移容器，执行 `prisma migrate deploy`。
4. 仅在迁移容器成功退出后，更新 API 和 Web。

每次执行都会新建迁移任务，不复用上次成功状态。直接运行 `docker compose --profile app up` 时，API 也依赖 `migrate` 成功完成；正式更新建议统一使用 `npm run deploy`。

首次迁移完成后，按 [生产初始化说明](./PRODUCTION_INITIALIZATION.md) 初始化基础计价数据和正式管理员。部署脚本不自动创建管理员或演示数据。全部业务验收通过前不要开放用户流量。

## 已有数据库接入

先备份数据库，保留当前应用版本和迁移日志；在数据库副本验证后再操作实际环境。接管期间停止其他部署和数据库结构变更。

### 当前结构完整，但没有完整迁移记录

适用于此前使用 `prisma db push`，或手工建表后已经与当前 `schema.prisma` 完全一致的数据库。

```bash
npm run db:adopt
npm run db:deploy
npm run db:status
```

`db:adopt` 先比较实际结构与当前 Prisma 模型。存在结构差异、未解决的失败迁移、历史文件校验和不一致或未知的有效迁移记录时，命令退出，不补记历史。

检查通过后，只为缺失的迁移写入已应用记录，不重跑建表 SQL，不修改业务数据。若补记过程被中断，可以核对状态后重试。该命令只用于首次接管，不应放入自动发布流程，也不能用于绕过失败迁移。

### 保留历史结构和部分迁移记录的旧库

仓库保留原有六份迁移，并新增 `20260801000000_initial_schema` 起始迁移及 `20260909000000_align_current_schema` 修正迁移。

旧库可能已经存在起始表结构，但缺少起始迁移记录。不要直接执行起始建表 SQL，也不要对不匹配当前模型的库运行接管命令来强行跳过升级。

1. 在副本核对实际结构、`_prisma_migrations` 与已经执行的历史迁移。
2. 在独立空库重放到相同历史版本，比较结构，确认旧库已包含起始迁移的全部效果。原有额外表、字段或缺失约束都需要人工核对。
3. 仅在确认缺失的是起始迁移记录时，在 API 目录执行以下命令补记：

```bash
npx prisma migrate resolve --applied 20260801000000_initial_schema --schema prisma/schema.prisma
```

4. 回到项目根目录，执行 `npm run db:deploy` 和 `npm run db:status`，再验证数据和业务接口。

旧迁移包含清理聊天消息及通知、合并用户角色、删除密码字段等历史行为。这些是升级原有行为；升级较老数据库前，应检查涉及数据并保留备份。

## 发布失败处理

- 迁移失败时，部署脚本以非零状态退出，不执行更新 API 和 Web 的命令。已有应用容器不在此步骤主动停止，但数据库可能已发生部分变化。
- 保存迁移名称、错误日志、数据库备份和旧版镜像。检查失败 SQL 是否已部分执行，以及旧应用是否仍兼容。
- `migrate deploy` 不提供自动数据库回滚。不能仅通过回退代码来恢复已删除的数据。
- 在副本验证修复后，决定完成未执行步骤，或撤销已执行步骤。只有实际数据库状态确认后，才使用 Prisma 的 `migrate resolve --applied` 或 `--rolled-back` 修复记录并重试。
- 不在生产执行 `migrate reset`、`db push --accept-data-loss`，也不通过删除迁移记录绕过错误。

## 验证范围

自动测试使用独立 PostgreSQL schema，验证空库迁移、结构一致性、重复执行、旧用户及需求和通知数据保留、失败迁移阻断，以及已有库接管。测试结束仅清理本次创建的 schema。

```bash
TEST_DATABASE_URL='<独立测试库连接地址>' npm test
```

未设置 `TEST_DATABASE_URL` 时，数据库集成测试会跳过。发布顺序和失败阻断测试仍会执行。

部署脚本完成不代表已可对外开放：仍需验证 API 就绪、HTTPS 登录、模型上传下载及联系方式申请闭环。现有 `/health/ready` 只验证数据库和 Redis 连通性，不能替代迁移状态与业务验收。
